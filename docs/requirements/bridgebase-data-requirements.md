# BridgeBaseのデータ利用要件

## 目的

BridgeBaseで必要となるデータの保持・検索・参照・更新要件を整理し、橋梁データのER設計に用いる入力条件を確定する。

## 対象範囲

現時点でxROADから無償公開されている橋梁データを対象とする。

有償データ、今後追加される未確定項目、他データセットとの統合については対象外とする。

複数の橋梁にわたる過去の点検結果の横断検索、点検結果の年度別集計、判定区分の遷移分析およびその表示方法は本Issueでは定義せず、別途扱う。

## 設計上の位置づけ

本書で用いる「論理的な橋梁」「論理的な点検結果」「基本情報の観測単位」は、利用上区別して扱う必要がある情報の単位を示す。これらを独立したエンティティまたはテーブルとして実装することを本書で決定するものではなく、具体的な構成はIssue #24で判断する。

## 履歴要件

- REQ-005の基本情報履歴は将来要件とし、初期段階のデータベースでは現在の基本情報を通常参照の対象とする。
- 取得時点ごとの基本情報はrawデータから再現・検証できるよう保持する。将来REQ-005へ対応する場合の差分判定、保持単位および参照方法は、その時点で別途決定する。
- 同じ橋梁について点検年度が異なる点検結果を区別して保持し、年度をまたぐ点検履歴を参照できること。
- 同一橋梁かつ同一点検年度の点検結果を再取得した場合は、判定区分や措置状況等が変化していても、同一の論理的な点検結果に対する見直しとして現在値へ反映し、重複して追加しない。見直し前の内容はデータベースの点検履歴には保持せず、取得日時ごとのrawデータで追跡する。
- 橋梁の最新の点検結果は、保持している点検結果のうち点検年度が最も新しいものとする。
- `koushin_nichiji`はxROAD上の橋梁レコードの更新日時を示す出典メタデータとして保持するが、点検結果の新旧および同一性の判定には使用しない。`koushin_nichiji`のみの変化は点検内容の変化とはみなさない。
- 点検履歴の検索・参照では、各点検年度について見直し後の現在値を使用し、過去の取得時点で公表されていた値は再現しない。

## 更新・再取込要件

- 同じ取得データを複数回取り込んでも、論理的な橋梁および論理的な点検結果が重複せず、業務データとしてのデータベース状態が変わらないこと。新しい取得で橋梁基本情報および点検内容が前回と同一の場合も、論理データを重複して追加しない。
- 正常な全件取得に含まれるデータで、保持対象の基本属性、判定区分または措置状況が未提供もしくは`null`になった場合は、不明な値として`null`を保持し、前回の値で補完しない。非`null`と`null`の差異も現在の基本情報または同一点検年度の点検結果の現在値への反映対象とする。ただし、橋梁または点検結果の識別に必要な項目が欠けている場合は取り込まず、取込エラーとして扱う。
- 正常に完了した同一範囲の全件取得で、以前に取得した橋梁が取得結果に含まれなくなった場合も、当該橋梁および関連する点検履歴を物理削除しない。
- 最新の正常な同一範囲の全件取得で確認できなかった橋梁は、廃止された可能性があるものの廃止とは断定せず、「最新取得で未観測」として扱う。通常の地図表示および最新状態の検索からは除外するが、橋梁情報と点検履歴は引き続き参照可能とする。後の取得で再び確認できた場合は通常表示の対象へ戻す。未観測判定の基準とする取得範囲および重複する取得範囲の扱いは、未解決事項の決定に従う。
- 1回の取得範囲に含まれるデータベース更新は、すべての更新に成功した場合だけ反映する。途中で失敗した場合は、その取込による変更を残さず、取込前の状態を維持する。
- 取得日時が古いデータを後から取り込んでも、橋梁の現在の基本情報、同一点検年度の現在値、および最新取得での観測状態を過去の状態へ戻さない。ただし、データベースに存在しない過去年度の点検結果は履歴として追加できる。取得データ間の新旧はBridgeBaseの取得日時で判断し、`koushin_nichiji`は使用しない。

## データ保持要件

- 取得をまたいで同一橋梁を追跡し、現在の基本情報、年度ごとの点検結果、および現在値の新旧を判断するための取得日時を参照できるよう、必要な情報をデータベースへ保持する。具体的なエンティティ構成はIssue #24で決定する。REQ-006の集約結果は保持した情報から導出し、永続的な保持を必須としない。
- データベースに登録した橋梁の基本情報および点検履歴には期間による自動削除を設けず、橋梁が最新取得で未観測になった後も保持する。削除が必要になった場合は、別途定める明示的な運用判断によって行う。
- rawデータは取得日時および取得範囲と対応付け、各取得時点でxROADから得た内容を後から再現・検証できる形で外部ストレージへ保持し、Gitでは管理しない。取得ごとの完全なスナップショットとするか、基準データと増分の組合せとするかはIssue #29で決定する。
- rawデータの保持期間および削除条件はIssue #29で定め、保持方針が決まるまでは自動削除しない。

## 未解決事項

### 橋梁識別子の安定性

現在の基本情報の更新、点検履歴、同一内容の重複防止および未観測判定には、取得をまたいで同一橋梁を識別できる必要がある。使用する識別情報はIssue #26で検証し、その結果を親Issue #24のER設計へ反映する。本Issueでは主キーおよび一意制約を決定しない。

### 取得範囲と観測状態

取得範囲を一意に識別する必要がある。複数の取得範囲が重複する場合、1つの取得範囲で未観測だったことだけを理由に、BridgeBase全体で未観測とは判定できない。未観測判定の基準とする取得範囲、および重複する取得範囲で観測状態が異なる場合の扱いはIssue #28で整理し、その結果を本要件文書および親Issue #24のER設計へ反映する。

### 同一橋梁・同一年度の複数点検

初期スコープでは、同一橋梁かつ同一点検年度を1つの論理的な点検結果として扱う。ただし、独立した複数の点検結果が存在する場合に別の点検結果を上書きする可能性があるため、Issue #26で公式仕様または実データを基に該当ケースの有無を確認し、その結果を親Issue #24へ反映する。存在が確認された場合は、点検結果の同一性条件を見直す。

### 橋梁と行政区域の関係

現在確認済みの八潮市データでは、1つの橋梁に対して1組の行政区域が含まれている。一方、1つの橋梁が複数の行政区域に関係する場合に、xROAD上でどのように表現されるか、およびBridgeBaseで複数区域との関係を保持する必要があるかは未確認である。

ER設計で橋梁と行政区域のカーディナリティを決定する前に、公式仕様または実データを基に確認する。この調査はIssue #27で行い、結果を本要件文書および親Issue #24のER設計へ反映する。
