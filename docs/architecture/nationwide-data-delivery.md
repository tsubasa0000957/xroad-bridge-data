# 全国展開に向けたデータ配信方式

## ステータス

採用

## 背景

BridgeBaseは、xROADの橋梁データを取得・正規化し、地図上へ表示するMVPとして開発している。
現在は任意の市区町村コードを指定して、その自治体の橋梁を全件取得できる。将来的には全国約73万橋を対象としたいが、
単一のGeoJSONをブラウザで全件読み込み・描画する現在の構成は、そのまま全国規模へ拡大することが難しい。
全国対応の実装を始める前に、データの保存・配信・描画方式を比較し、次の開発段階で採用する構成を決定する。

## 現在の構成

```text
xROAD API
    ↓
scripts/fetch_bridges.sh
    ↓
data/raw/<市区町村コード>.json
    ↓
scripts/normalize.py
    ├── data/processed/processed.csv
    └── data/processed/processed.geojson
                         ↓
                    web/app.js
                         ↓
                  Leafletで地図表示
```

- `fetch_bridges.sh`は市区町村コードを受け取り、5,000件単位でページングして、取得結果を1つのJSONへまとめる。
- `normalize.py`は入力JSONから必要な項目を抽出し、固定名のCSVとGeoJSONへ変換する。
- 新しい自治体を正規化すると、以前のprocessedデータは上書きされる。
- フロントエンドは`processed.geojson`全体を読み込み、LeafletのGeoJSONレイヤーとして全件を一度に描画する。
- バックエンドAPIやデータベースは使用していない。
- rawデータとprocessedデータはGitリポジトリ内で管理している。

## 全国展開時の要件

### 必須要件

- 全国約73万橋を地図上で扱えること
- 初期表示時に全国の全データをブラウザへ一括送信しないこと
- 地図の表示範囲とズームレベルに応じて、必要なデータだけを表示できること
- 橋梁を選択すると、橋梁名や路線名などの属性を確認できること
- データ更新処理を再実行でき、同じ手順で配信用データを生成できること
- rawデータと生成データをGitリポジトリから分離できること

### 将来要件

- 自治体、管理者、判定区分などで絞り込めること
- 橋梁名や路線名などで検索できること
- データの差分更新に対応できること
- 定期的なデータ更新を自動化できること
- 橋梁ごとに複数年度の点検結果を履歴として保持し、時系列で参照できること

### 運用上の要件

- 個人開発で維持できる実装・運用コストであること
- 最初は小さく導入し、必要に応じて機能を追加できること
- 現在の取得・正規化処理を可能な範囲で再利用できること

## 候補

### 静的ベクトルタイル／PMTiles

```text
xROAD API
    ↓
取得・正規化
    ↓
ベクトルタイル生成
    ↓
bridges.pmtiles
    ↓
静的ホスティング／オブジェクトストレージ
    ↓
MapLibre GL JS
```
PMTilesは、複数のズームレベルからなるタイルを1つのアーカイブへ格納する形式である。ブラウザはHTTP Range Requestを使用して、表示範囲に必要な部分だけを取得する。
実行時のデータベースやバックエンドAPIを必要としないため、構成と運用コストを抑えやすい。一方、読み込まれていない全国データを対象とした検索や複雑な絞り込みには向かず、
データ更新時は基本的にアーカイブを再生成して置き換える必要がある。
現在使用しているLeafletでもPMTilesを扱えるが、インタラクティブなベクトルタイルにはMapLibre GL JSが推奨されている。

### PostGIS＋API

```text
xROAD API
    ↓
取得・正規化
    ↓
PostgreSQL／PostGIS
    ↓
API
    ↓
表示範囲・検索条件に一致するデータ
    ↓
フロントエンド
```
橋梁の位置と属性をPostGISへ保存し、フロントエンドから受け取った表示範囲や検索条件に応じて、APIが必要なデータだけを返す構成である。
空間インデックスを利用して表示範囲内の橋梁を検索できる。APIの応答形式にはGeoJSONや、PostGISで生成したベクトルタイルを使用できる。
検索、絞り込み、差分更新へ柔軟に対応できる一方、データベースとAPIの構築、デプロイ、監視、バックアップが必要となり、実装と運用が複雑になる。

### ハイブリッド構成

```text
                  ┌→ PMTiles → 地図表示
取得・正規化 ────┤
                  └→ PostGIS＋API → 検索・詳細取得
```
地図表示にはPMTilesを使用し、全国検索や複雑な絞り込みにはPostGISとAPIを使用する構成である。
静的配信の表示性能と、データベースによる検索の柔軟性を両立できる。一方、同じ橋梁データをPMTilesとPostGISの両方で管理するため、
更新時の同期処理が必要となる。3候補の中で実装と運用が最も複雑である。

## 比較

| 比較観点 | 静的ベクトルタイル／PMTiles | PostGIS＋API | ハイブリッド構成 |
| --- | --- | --- | --- |
| 表示性能 | 必要なタイルだけを取得し、WebGLで描画できる | 空間インデックスとAPI設計により高い性能を実現できる | 地図表示はPMTilesを使うため高い |
| 検索・絞り込み | 読み込み済みデータに限られ、全国検索には別の仕組みが必要 | 属性・位置を条件として柔軟に検索できる | APIにより柔軟に検索できる |
| データ更新 | アーカイブを再生成して置き換える | レコード単位や差分で更新できる | PMTilesとPostGISの両方を更新・同期する必要がある |
| 実装の複雑さ | 中。タイル生成処理とフロントエンド変更が必要 | 高。データベースとAPIの構築が必要 | 非常に高。2つの配信経路と同期処理が必要 |
| 運用コスト | 低。静的ホスティングまたはオブジェクトストレージで配信できる | 中〜高。データベースとAPIを常時運用する | 高。静的配信とバックエンドの両方を運用する |
| フロントエンド | LeafletからMapLibre GL JSへの移行が必要 | GeoJSONならLeafletを継続可能。ベクトルタイルなら変更が必要 | MapLibre GL JSと検索APIの連携が必要 |
| Git管理からの分離 | 生成したPMTilesを外部ストレージへ配置する | データをPostGISへ保存する | PMTilesとPostGISの両方をリポジトリ外で管理する |
| 既存処理の再利用 | 取得処理を再利用し、正規化後にタイル生成処理を追加する | 取得処理を再利用し、正規化結果をPostGISへ投入する | 取得・正規化処理を再利用し、両方の出力を生成する |
| 履歴管理 | 年度ごとの別アーカイブは作れるが、横断的な参照が難しい | 橋梁と点検結果を分け、年度ごとの履歴を保持・検索できる | PostGISで履歴を管理し、PMTilesには最新状態を反映できる |

## 決定

全国展開に向けたデータの保存・配信方式として、PostGIS＋APIを採用する。
橋梁の基本情報と点検結果の履歴をPostgreSQLへ保存し、位置情報の管理と表示範囲検索にはPostGISを使用する。フロントエンドはAPIを通して、表示範囲や検索条件に一致するデータだけを取得する。
初期段階では、APIから表示範囲内の橋梁をGeoJSONとして返し、現在のLeafletを継続して使用する。全国規模での性能検証後、必要に応じてベクトルタイルやPMTilesの追加を検討する。
一定のズームレベル未満では個別の橋梁を取得せず、将来的に件数の集約表示を検討する。

取得したraw JSONはGitで管理せず、取得日時ごとのスナップショットとして外部ストレージへ保存する。正規化した橋梁と点検結果はPostgreSQL／PostGISへ保存する。具体的なストレージサービスは別Issueで決定する。

## 判断理由

BridgeBaseでは、全国の橋梁を表示するだけでなく、点検結果を継続的に蓄積・分析し、自治体、管理者、判定区分などの条件で検索・絞り込みできることを重視する。
PostgreSQLでは、橋梁の基本情報と年度ごとの点検結果を分けて管理し、1つの橋梁に複数の点検結果を関連付けられる。さらにPostGISの空間インデックスを利用することで、地図の表示範囲に含まれる橋梁を効率よく検索できる。
静的ベクトルタイル／PMTilesは全国地図の表示には適しているが、点検履歴の蓄積や全国データを対象とした検索には別の仕組みが必要になる。ハイブリッド構成は両方の利点を得られる一方、初期段階では実装と運用が複雑になりすぎるため採用しない。
初期段階では動的GeoJSONを使用することで、現在のLeafletを再利用しながら、PostGISへの保存、表示範囲検索、条件検索、点検履歴の管理を先に検証できる。また、将来必要になった場合は、PostGISからベクトルタイルを生成する構成へ拡張できる。

## 段階的な移行案

### 1. データモデルを設計する

- 橋梁の基本情報を保持する`bridges`テーブルを設計する
- 年度ごとの点検結果を保持する`inspections`テーブルを設計する
- 同じ橋梁を継続的に識別するキーを決定する
- 点検結果の重複登録を防ぐ制約を決定する

### 2. 八潮市のデータをPostGISへ登録する

- ローカル開発用のPostgreSQL／PostGIS環境を用意する
- 既存の八潮市182件を登録する処理を作成する
- 橋梁と点検結果が分かれて保存されることを確認する
- 同じデータを再登録しても重複しないことを確認する

### 3. 表示範囲検索APIを作成する

- 地図の表示範囲を表すbboxとズームレベルを受け取る
- 低ズームでは個別の橋梁を返さない
- PostGISで表示範囲内の橋梁を検索する
- 検索結果をGeoJSONとして返す
- 取得件数の上限や入力値の検証を追加する

### 4. フロントエンドを動的GeoJSONへ移行する

- 固定の`processed.geojson`の読み込みを廃止する
- 地図の移動やズームに応じてAPIを呼び出す
- APIから取得した表示範囲内の橋梁だけを描画する
- 現在のポップアップ表示を維持する

### 5. 検索・履歴参照を追加する

- 自治体、管理者、判定区分による絞り込みを追加する
- 橋梁名や路線名による検索を追加する
- 橋梁ごとの点検履歴を取得・表示する

### 6. 対象地域を段階的に拡大する

- 複数自治体、都道府県、全国の順にデータを増やす
- データ量ごとにAPIと描画の性能を計測する
- 必要になった時点でベクトルタイルやPMTilesを検討する

## スコープ外

この文書では構成方針の決定のみを行い、以下の実装や技術選定は対象外とする。

- PostgreSQL／PostGIS環境の構築
- テーブル定義とマイグレーションの作成
- データ登録処理の実装
- APIの言語、フレームワーク、ホスティング先の選定
- APIおよびフロントエンドの実装
- 全国データの取得と登録
- ベクトルタイルやPMTilesの生成・配信
- リトライや定期更新処理の実装
